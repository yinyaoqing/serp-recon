# Before you write the parser: a reachability audit of eight targets

*Measured 2026-09-22. One request per target, from a residential connection in
Taiwan, using `curl` with an ordinary Chrome user agent. Everything below is
reproducible with `bin/serp-recon probe`.*

*Re-verified 2026-10-12: all eight results unchanged.*

*繁體中文版：[recon-2026-09-22.zh-TW.md](recon-2026-09-22.zh-TW.md)*

I wanted to build a SERP parser as a weekend project. I picked the target first
and did the recon second, which is the wrong order, and it nearly cost me the
weekend before I noticed. This is what I should have done first, and what it
found.

The question is narrow: **can a plain HTTP client fetch this page?** Not "is
there a way in" — there is almost always a way in, given enough money and
maintenance. The useful question before committing a weekend is whether the
cheapest possible client works, because if it does not, everything about the
project changes: the budget, the failure modes, the test strategy, and whether
the repo will still run six months from now.

## The results

| Target | HTTP | Verdict |
|---|---|---|
| Wikipedia `Special:Search` | 200 | reachable, server-rendered, 20 results |
| Google Books SERP (`tbm=bks`) | 200 | JS gate, 0 results in the body |
| `books.google.com` legacy search | 302 to 200 | redirects into the same JS gate |
| Google Books API v1 (no key) | 429 | shared anonymous quota, exhausted |
| g2.com product reviews | 403 | DataDome, behind Cloudflare |
| g2.com sitemap (listed in its own robots.txt) | 403 | DataDome |
| Trustpilot review page | 403 | blocked |
| Qwant search API | 403 | blocked |

One of eight. That ratio is not a complaint — it is the entire reason a
commercial SERP API has customers.

## HTTP 200 is not a successful fetch

The Google Books result is the one worth dwelling on, because it is the failure
mode that silently poisons a scraper.

```
$ curl -s -o out.html -w "%{http_code} %{size_download}b\n" \
    -H "User-Agent: Mozilla/5.0 ... Chrome/131.0.0.0 Safari/537.36" \
    "https://www.google.com/search?tbm=bks&q=ruby+programming"
200 45690b
```

Two hundred. Forty-five kilobytes. Zero results:

```html
<noscript>
  <meta content="0;url=/httpservice/retry/enablejs?sei=..." http-equiv="refresh">
  <div style="display:block">Please click
    <a href="/httpservice/retry/enablejs?sei=...">here</a>
    if you are not redirected within a few seconds.</div>
</noscript>
```

Google served a JavaScript bootstrap shell. A parser pointed at this does not
crash — it finds no result containers, returns an empty array, and reports
success. Wire that to a cron job and you will collect empty result sets for
weeks while every dashboard stays green.

I tried the usual escapes. `gbv=1`, the old "basic version" parameter: still
gated. An ancient Firefox 60 user agent, on the theory that Google serves
simpler HTML to older clients: still gated. A Lynx user agent: 1,173 bytes of
nothing. The legacy `books.google.com/books?q=` endpoint 302s straight back to
`google.com/search?tbo=p&tbm=bks`, into the same shell.

So this repo's `Fetcher` treats a JS shell as a **failure**, with its own error
class, and does not retry it. Retrying a 429 makes sense. Retrying a
deterministic architectural mismatch just burns the rate limit you are already
close to.

## g2.com: three different kinds of "no", and they disagree

g2.com was the target I actually wanted — it is the highest-voted unclaimed
new-API request on SerpApi's public roadmap, open since 2022. It turned out to be
the most interesting failure, because its three layers of "no" contradict each
other.

**Layer one, robots.txt.** I read the whole file rather than grepping it, which
matters here. It contains three kinds of block. The `User-agent: *` block
disallows tracking parameters, `/login`, `/admin`, `/search/*`, and a scattering
of product subpaths — but *not* `/products/*/reviews`. A separate block covering
`GPTBot`, `ClaudeBot`, `Google-Extended`, `CCBot` and friends *does* disallow
`/products/*/reviews/*`. A third block hands `Disallow: /` to a list of scrapers
and mirroring tools ending in `Bytespider` and `DeepSeekBot`.

So the stated policy is: general crawlers may read product reviews; AI training
crawlers may not.

**Layer two, `llms.txt`.** g2.com publishes one, and it is unusually
cooperative. It documents the URL patterns explicitly, for machines:

```
Product review pages: https://www.g2.com/products/{product-slug}/reviews
Product pricing:      https://www.g2.com/products/{product-slug}/pricing
```

Their `/ai-instructions` page goes further: *"Everything on this page is
published for human readers and machine readers alike. There is no separate
version served to automated clients."*

**Layer three, the WAF.** Every one of those documented URLs returns 403:

```
HTTP/1.1 403 Forbidden
Set-Cookie: datadome=gqLZsu9gdiDWEvX~cCUhNwFGnWSY5fIq~...
Set-Cookie: __cf_bm=wN9epR9vrEk65rTpdC0ekOMzRoki0foRC7jT5wr6h7A-...
Server: cloudflare
CF-RAY: a3efaa829d13ce51-SIN
```

Including the sitemap that their own robots.txt advertises on line 1.

Note the layering, because it changes the estimate. `Server: cloudflare` and
`__cf_bm` are the CDN. The actual bot decision is DataDome — a dedicated
anti-bot vendor whose product is specifically tuned against headless browsers
and TLS-fingerprint impersonation. Cloudflare alone is sometimes a fingerprint
problem you can solve once. DataDome is a residential-proxy-and-real-browser
problem, permanently, with a vendor shipping updates against you.

The lesson is not that g2 is hostile. It is that **robots.txt, `llms.txt` and the
WAF are three independent systems that nobody reconciled**, and only one of them
is load-bearing. Reading robots.txt told me which paths were *stated* to be
allowed. One `curl` told me which were *actually* served. Those are different
questions and you need both answers.

There is a third question neither of them answers: the Terms of Service.
robots.txt declining to disallow a path is not consent. This audit takes no
position on it — but if you are publishing a scraper, that is a question to
settle deliberately rather than by omission.

## What survives

Wikipedia's `Special:Search`, and it is almost quaint about it:

```html
<li class="mw-search-result">
  <div class="mw-search-result-heading">
    <a href="/wiki/Ruby_(programming_language)"
       title="Ruby (programming language)" data-serp-pos="0">
      <span class="searchmatch">Ruby</span> (<span class="searchmatch">programming</span> language)
    </a>
  </div>
  <div class="searchresult">...</div>
</li>
```

Stable class names. A `data-serp-pos` attribute giving you the rank directly
instead of making you count. A `<span class="searchmatch">` around each term the
site itself matched on. And on the results header,
`data-mw-num-results-total="10459"` — the total as an integer attribute, rather
than a localised string like "About 10,459 results" that you would have to parse
differently for every language you support.

It also has something rarer: an independent answer. The MediaWiki API serves the
same query, so the scrape can be *checked* rather than merely exercised:

```
scraped   data-mw-num-results-total  = 10459
API       query.searchinfo.totalhits = 10459
```

Most scraper test suites can only assert that parsing ran and produced
plausibly-shaped output. If your target publishes an API over the same data, you
can assert that parsing produced the *right* output — and you should. It is the
difference between a test that catches a redesign and a test that catches a
crash.

## What the audit changed in the parser

Three things, all of them consequences of the recon rather than decisions made
up front.

**Selector drift raises, by name.** The nightmare is not a parser that breaks.
It is one that half-breaks and keeps running. Each engine declares its required
selectors, and the base class checks them before any field is read:

```
[wikipedia] required selector "li.mw-search-result" matched nothing.
Page title was "Search results". The page layout probably changed;
re-record the fixture and update the parser.
```

**Fixtures are recorded with provenance.** Every fixture logs the date and the
exact request that produced it, so re-recording after a redesign is mechanical
rather than archaeological.

**The dead ends stay in the repo.** The Google Books JS shell is checked in as a
fixture, with a test asserting it still contains `enablejs` and still contains no
book links. It is the cheapest possible regression test for "has this become
fetchable yet?", and it stops the next person — me, in four months — from
rediscovering the gate from scratch.

## The actual conclusion

The recon took about fifteen minutes. The weekend I nearly spent fighting
DataDome would have produced a repository that returns 403 on a reviewer's
machine, and the skill it demonstrated would have been *I can afford residential
proxies*.

Fifteen minutes of `curl` and one careful read of a robots.txt reordered the
entire project: different target, different architecture, a test suite with
ground truth, and a repo that actually runs when someone clones it.

Do the audit first. It is the cheapest part of the project, and it is the part
that decides what the project is.
