# 寫爬蟲之前：八個目標的可達性稽核

*2026-09-22。每個目標各發一個請求，從台灣的住宅網路，用 `curl` 搭配一般的 Chrome user agent。以下所有數字都可以用 `bin/serp-recon probe` 重現。*

我本來想利用週末寫一支搜尋結果解析器。我先挑了目標，才做偵察——順序是反的，而這個錯誤差點讓我白費整個週末。

這篇記錄的是我應該先做的事，以及它查出了什麼。

問題很窄：**一個最陽春的 HTTP client，拿不拿得到這個頁面？**

不是「有沒有辦法進去」。只要錢和維護力氣夠，幾乎總是有辦法。但在投入一個週末之前，該問的是最便宜的做法行不行得通——因為如果不行，這個專案的一切都會改變：預算、失敗模式、測試策略，以及半年後它還跑不跑得動。

## 結果

| 目標 | HTTP | 判定 |
|---|---|---|
| 維基百科 `Special:Search` | 200 | 可達，伺服器端渲染，20 筆結果 |
| Google 圖書搜尋（`tbm=bks`） | 200 | JS 空殼，內容零筆 |
| `books.google.com` 舊版搜尋 | 302 → 200 | 轉址到同一個空殼 |
| Google Books API v1（無金鑰） | 429 | 匿名共用配額已耗盡 |
| g2.com 產品評論 | 403 | DataDome，架在 Cloudflare 之後 |
| g2.com 網站地圖（robots.txt 自己公告的） | 403 | DataDome |
| Trustpilot 評論頁 | 403 | 被擋 |
| Qwant 搜尋 API | 403 | 被擋 |

八個裡面一個。

這不是抱怨。**這個比例本身，就是商用搜尋結果 API 有客戶的全部理由。**

## HTTP 200 不等於抓到了

Google 圖書這一筆值得多講兩句，因為它是最會安靜毒害一支爬蟲的失敗模式。

```
$ curl -s -o out.html -w "%{http_code} %{size_download}b\n" \
    -H "User-Agent: Mozilla/5.0 ... Chrome/131.0.0.0 Safari/537.36" \
    "https://www.google.com/search?tbm=bks&q=ruby+programming"
200 45690b
```

兩百。四十五 KB。零筆結果：

```html
<noscript>
  <meta content="0;url=/httpservice/retry/enablejs?sei=..." http-equiv="refresh">
  <div style="display:block">Please click
    <a href="/httpservice/retry/enablejs?sei=...">here</a>
    if you are not redirected within a few seconds.</div>
</noscript>
```

Google 回的是一個 JavaScript 啟動殼。

一支解析器指向這種頁面**不會當掉**。它找不到任何結果容器，回傳一個空陣列，然後回報成功。把它接上排程每天跑，你會連續幾週蒐集到空的結果集，而所有監控畫面一路綠燈。

我試過常見的幾條繞路。`gbv=1`——Google 的「基本版」參數：一樣被擋。偽裝成老舊的 Firefox 60，賭 Google 會對舊瀏覽器送簡化 HTML：一樣被擋。Lynx 的 user agent：回了 1,173 位元組的空白。舊的 `books.google.com/books?q=` 端點直接 302 轉回 `google.com/search?tbo=p&tbm=bks`，同一個殼。

所以這個專案的 `Fetcher` 把 JS 空殼當成**失敗**，給它自己的錯誤類別，而且**不重試**。

重試 429 有道理。重試一個確定性的架構不匹配，只是把你本來就快用完的請求額度燒掉。

## g2.com：三種不同的「不行」，而且互相矛盾

g2.com 才是我原本想做的目標——它在 SerpApi 的公開 roadmap 上是票數最高、沒人認領的新 API 請求。

結果它是最有意思的一次失敗，因為它的三層「不行」彼此打架。

**第一層，robots.txt。** 我把整個檔案讀完，而不是用 grep 掃——這在這裡有差。

檔案裡有三種區塊。`User-agent: *` 區塊禁止追蹤參數、`/login`、`/admin`、`/search/*`，以及零星幾個產品子路徑——但**不包含** `/products/*/reviews`。另一個涵蓋 `GPTBot`、`ClaudeBot`、`Google-Extended`、`CCBot` 的區塊，**則明確禁止** `/products/*/reviews/*`。第三個區塊把 `Disallow: /` 發給一串爬蟲與整站下載工具，結尾是 `Bytespider` 和 `DeepSeekBot`。

所以它宣告的政策是：一般爬蟲可以讀產品評論，AI 訓練爬蟲不行。

**第二層，`llms.txt`。** g2.com 有發布這個檔案，而且態度異常友善。它把網址格式**一條一條列給機器看**：

```
Product review pages: https://www.g2.com/products/{product-slug}/reviews
Product pricing:      https://www.g2.com/products/{product-slug}/pricing
```

它的 `/ai-instructions` 頁面講得更白：「這個頁面上的一切，同時發布給人類讀者與機器讀者。**我們不會對自動化客戶端提供另一個版本。**」

**第三層，防火牆。** 上面那些網址，每一個都回 403：

```
HTTP/1.1 403 Forbidden
Set-Cookie: datadome=gqLZsu9gdiDWEvX~cCUhNwFGnWSY5fIq~...
Set-Cookie: __cf_bm=wN9epR9vrEk65rTpdC0ekOMzRoki0foRC7jT5wr6h7A-...
Server: cloudflare
CF-RAY: a3efaa829d13ce51-SIN
```

**包括它自己 robots.txt 第一行公告的那個網站地圖。**

這裡要留意分層，因為它會改變你的成本估算。`Server: cloudflare` 和 `__cf_bm` 是 CDN 層。真正做出「擋掉」這個決定的是 DataDome——一家專做反爬的廠商，產品專門針對 headless 瀏覽器和 TLS 指紋偽裝而設計。

單純的 Cloudflare，有時候是一個解一次就過的指紋問題。DataDome 是住宅 IP 加真實瀏覽器的問題，而且是永久的——對面有一整個團隊持續更新來對付你。

這裡的教訓不是「g2 很兇」。而是：

> **robots.txt、`llms.txt`、防火牆，是三套沒人對齊過的系統，而且只有一套說了算。**

讀 robots.txt 告訴我哪些路徑「宣告上」是允許的。一個 `curl` 告訴我哪些路徑「實際上」拿得到。這是兩個不同的問題，兩個答案你都需要。

還有第三個問題，前兩者都沒有回答：**服務條款**。robots.txt 沒有禁止某條路徑，不等於它同意你爬。這篇稽核不對此表態——但如果你要公開發表一支爬蟲，這是一個應該刻意想清楚的問題，而不是靠略過來迴避。

## 活下來的那一個

維基百科的 `Special:Search`，而且它的做法幾乎有點古典：

```html
<li class="mw-search-result">
  <div class="mw-search-result-heading">
    <a href="/wiki/Ruby_(programming_language)"
       title="Ruby (programming language)" data-serp-pos="0">
      <span class="searchmatch">Ruby</span> (<span class="searchmatch">programming</span> language)
    </a>
  </div>
  <div class="searchresult">...</div>
</li>
```

class 名稱穩定。有一個 `data-serp-pos` 屬性直接給你名次，不必自己數。每個被命中的關鍵字外面包著 `<span class="searchmatch">`，等於網站主動告訴你它為什麼回傳這筆結果。而在結果標頭上，`data-mw-num-results-total="10459"`——總數是一個整數屬性，不是「約 10,459 項結果」這種還要按語言分別解析的在地化字串。

它還有一個更稀有的東西：**一個獨立的答案**。

MediaWiki API 提供同一筆查詢，所以這次爬取可以被**驗證**，而不只是被執行：

```
爬取所得   data-mw-num-results-total  = 10459
官方 API   query.searchinfo.totalhits = 10459
```

大多數爬蟲的測試，只能斷言「解析跑完了」「輸出的形狀看起來合理」。如果你的目標有一個涵蓋同一批資料的官方 API，你就能斷言解析出來的**內容是對的**——而且你應該這麼做。

這是「抓得到改版」和「只抓得到當機」之間的差別。

## 稽核改變了解析器的哪些設計

三件事，全都是偵察的結果，而不是我事先想好的。

**一、選擇器失效要指名道姓地爆掉。**

惡夢不是解析器壞掉，是它**半壞不壞地繼續跑**。每個引擎宣告自己必須命中的選擇器，基底類別在讀取任何欄位之前先檢查：

```
[wikipedia] required selector "li.mw-search-result" matched nothing.
Page title was "Search results". The page layout probably changed;
re-record the fixture and update the parser.
```

**二、測試樣本要記錄來源。**

每一份樣本都記下錄製日期和產生它的確切請求，這樣改版之後重錄是機械動作，而不是考古。

**三、走不通的路留在專案裡。**

Google 圖書那個 JS 空殼被存成測試樣本，附一條測試斷言它「仍然含有 `enablejs`」且「仍然沒有任何書籍連結」。這是「這條路通了沒？」最便宜的回歸測試，而且它會阻止下一個人——四個月後的我——從頭再發現一次同樣的事。

## 真正的結論

這次偵察大概花了十五分鐘。

而我差點拿去跟 DataDome 硬碰的那個週末，產出會是一個在審閱者電腦上回 403 的專案，它證明的能力是「我付得起住宅代理」。

十五分鐘的 `curl`，加上一次認真讀完的 robots.txt，重新排定了整個專案：不同的目標、不同的架構、一套有標準答案的測試，以及一個別人 clone 下來真的跑得動的 repo。

**先做稽核。它是整個專案裡最便宜的一段，也是決定這個專案到底是什麼的那一段。**
