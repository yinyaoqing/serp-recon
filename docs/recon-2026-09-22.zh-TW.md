# 動手寫爬蟲之前，先確認抓不抓得到：八個目標的實測

*2026-09-22 測得。每個目標各發一個請求，從台灣的住宅網路，用 `curl` 搭配一般的 Chrome user agent。以下所有數字都可以用 `bin/serp-recon probe` 重現。*

*2026-10-12 重新驗證，八筆結果完全相同。*

一般的流程是先選定目標，再動手寫解析程式。但在那之前，有一個更該先問的問題：

**一個最陽春的 HTTP client，拿不拿得到這個頁面？**

這跟「有沒有辦法進去」是兩回事。只要錢和維護力氣夠，幾乎總是有辦法。但在投入一個週末之前，該先確認最便宜的做法行不行得通——因為如果不行，這個專案的一切都會跟著改變：預算、會壞在哪裡、測試怎麼寫，以及半年後它還跑不跑得動。

## 結果

| 目標 | HTTP | 結果 |
|---|---|---|
| 維基百科 `Special:Search` | 200 | 抓得到，伺服器直接把內容吐出來，20 筆結果 |
| Google 圖書搜尋（`tbm=bks`） | 200 | 只有外框，內容零筆 |
| `books.google.com` 舊版搜尋 | 302 → 200 | 轉址到同一個空頁面 |
| Google Books API v1（無金鑰） | 429 | 匿名共用配額已耗盡 |
| g2.com 產品評論 | 403 | DataDome，架在 Cloudflare 之後 |
| g2.com 網站地圖（robots.txt 自己公告的） | 403 | DataDome |
| Trustpilot 評論頁 | 403 | 被擋 |
| Qwant 搜尋 API | 403 | 被擋 |

八個裡面一個。

這不是抱怨。**這個比例本身，就是商用搜尋結果 API 有客戶的全部理由。**

## HTTP 200 不等於抓到了

Google 圖書這一筆值得多講兩句，因為它是最容易讓一支爬蟲無聲無息壞掉的狀況。

```
$ curl -s -o out.html -w "%{http_code} %{size_download}b\n" \
    -H "User-Agent: Mozilla/5.0 ... Chrome/131.0.0.0 Safari/537.36" \
    "https://www.google.com/search?tbm=bks&q=ruby+programming"
200 45690b
```

兩百。四十五 KB。零筆結果：

```html
<noscript>
  <meta content="0;url=/httpservice/retry/enablejs?sei=..." http-equiv="refresh">
  <div style="display:block">Please click
    <a href="/httpservice/retry/enablejs?sei=...">here</a>
    if you are not redirected within a few seconds.</div>
</noscript>
```

Google 送回來的是一個只有外框的頁面，真正的內容要靠瀏覽器執行 JavaScript 再去拿一次。人用瀏覽器上網時，這件事是自動發生的，所以完全察覺不到；一支單純的程式不會照做，拿到的就是一個空頁面。

麻煩的是，程式**不會當掉**。它找不到任何一筆結果，回傳一個空陣列，然後回報成功。把它接上排程每天跑，你會連續幾週蒐集到空資料，而所有監控畫面一路綠燈。

常見的幾條繞路我都試過。`gbv=1`，Google 的「基本版」參數：一樣擋。偽裝成老舊的 Firefox 60，賭 Google 會對舊瀏覽器送簡化版 HTML：一樣擋。Lynx 的 user agent：回了 1,173 位元組的空白。舊的 `books.google.com/books?q=` 端點直接 302 轉回 `google.com/search?tbo=p&tbm=bks`，同一個頁面。

所以這個專案的 `Fetcher` 把這種回應當成**失敗**，給它自己的錯誤類別，而且**不重試**。

重試 429 有道理，等一下再來就好。但這種情況是架構上本來就不相容，重試幾次都一樣，只是把本來就快用完的額度燒掉。

## g2.com：三種不同的「不行」，而且互相矛盾

g2.com 才是原本想做的目標——它在 SerpApi 的公開 roadmap 上是票數最高、沒人認領的新 API 請求。

結果它是最有意思的一個，因為它的三層「不行」彼此打架。

**第一層，robots.txt。** 這裡值得把整個檔案讀完，而不是用 grep 掃過去。

檔案裡有三種區塊。`User-agent: *` 區塊禁止追蹤參數、`/login`、`/admin`、`/search/*`，以及零星幾個產品子路徑——但**不包含** `/products/*/reviews`。另一個涵蓋 `GPTBot`、`ClaudeBot`、`Google-Extended`、`CCBot` 的區塊，**則明確禁止** `/products/*/reviews/*`。第三個區塊把 `Disallow: /` 發給一串爬蟲與整站下載工具，結尾是 `Bytespider` 和 `DeepSeekBot`。

所以它寫出來的政策是：一般爬蟲可以讀產品評論，AI 訓練用的爬蟲不行。

**第二層，`llms.txt`。** g2.com 有發布這個檔案，而且態度異常友善。它把網址格式**一條一條列給機器看**：

```
Product review pages: https://www.g2.com/products/{product-slug}/reviews
Product pricing:      https://www.g2.com/products/{product-slug}/pricing
```

它的 `/ai-instructions` 頁面講得更白：「這個頁面上的一切，同時發布給人類讀者與機器讀者。**我們不會對自動化客戶端提供另一個版本。**」

**第三層，防火牆。** 上面那些網址，每一個都回 403：

```
HTTP/1.1 403 Forbidden
Set-Cookie: datadome=gqLZsu9gdiDWEvX~cCUhNwFGnWSY5fIq~...
Set-Cookie: __cf_bm=wN9epR9vrEk65rTpdC0ekOMzRoki0foRC7jT5wr6h7A-...
Server: cloudflare
CF-RAY: a3efaa829d13ce51-SIN
```

**包括它自己 robots.txt 第一行公告的那個網站地圖。**

這裡要留意是誰在擋，因為它會改變成本估算。`Server: cloudflare` 和 `__cf_bm` 是 CDN 那一層。真正做出「擋掉」這個決定的是 DataDome——一家專做反爬的廠商，產品就是針對 headless 瀏覽器和 TLS 指紋偽裝設計的。

單純的 Cloudflare，有時候是一個解一次就過的指紋問題。DataDome 則是要住宅 IP 加真實瀏覽器，而且永遠不會結束——對面有一整個團隊持續更新來對付你。

這裡的教訓不是「g2 很兇」，而是：

> **robots.txt、`llms.txt`、防火牆，是三套沒人對齊過的系統，而且只有一套說了算。**

讀 robots.txt 告訴你哪些路徑名義上是允許的。一個 `curl` 告訴你哪些路徑實際上拿得到。這是兩個不同的問題，兩個答案都需要。

還有第三個問題，前兩者都沒有回答：**服務條款**。robots.txt 沒有禁止某條路徑，不等於它同意你爬。這篇文章不對此下判斷——但如果要公開發表一支爬蟲，這是一個該刻意想清楚的問題，而不是靠略過來迴避。

## 活下來的那一個

維基百科的 `Special:Search`，而且它的做法相當老派：

```html
<li class="mw-search-result">
  <div class="mw-search-result-heading">
    <a href="/wiki/Ruby_(programming_language)"
       title="Ruby (programming language)" data-serp-pos="0">
      <span class="searchmatch">Ruby</span> (<span class="searchmatch">programming</span> language)
    </a>
  </div>
  <div class="searchresult">...</div>
</li>
```

class 名稱穩定。有一個 `data-serp-pos` 屬性直接給你名次，不必自己數。每個被命中的關鍵字外面包著 `<span class="searchmatch">`，等於網站主動告訴你它為什麼回傳這筆結果。結果標頭上還有 `data-mw-num-results-total="10459"`——總數是一個整數屬性，不是「約 10,459 項結果」這種還得按每種語言分別處理的字串。

它還有一個更難得的東西：**一份可以對照的標準答案**。

MediaWiki API 提供同一筆查詢，所以這次抓取可以被**驗證**，而不只是被執行：

```
抓取所得   data-mw-num-results-total  = 10459
官方 API   query.searchinfo.totalhits = 10459
```

大多數爬蟲的測試，只能確認「程式跑完了」「輸出的格式看起來合理」。如果目標網站有一個涵蓋同一批資料的官方 API，就能確認抓出來的**內容是對的**——而且應該這麼做。

這是「改版了會被測出來」和「只有當掉才會被測出來」的差別。

## 這次檢查改變了程式的哪些設計

三件事，全都是先檢查之後才決定的，不是事先想好的。

**一、選擇器失效要直接報錯，並說出是哪一個。**

最麻煩的情況不是程式壞掉，是它**半壞不壞地繼續跑**。所以每個引擎都先宣告自己一定要抓到的選擇器，在讀取任何欄位之前先檢查一遍：

```
[wikipedia] required selector "li.mw-search-result" matched nothing.
Page title was "Search results". The page layout probably changed;
re-record the fixture and update the parser.
```

一個改版後回傳 `{"title" => nil}` 的程式，可以安靜地跑一整個月。一個會講出「是這個選擇器不再匹配」的程式，當天下午就修好了。

**二、測試樣本要記錄來源。**

每一份樣本都記下錄製日期和產生它的確切請求，這樣網站改版之後重錄是機械動作，不用重新考古。

**三、走不通的路留在專案裡。**

Google 圖書那個空頁面被存成測試樣本，附一條測試確認它「仍然含有 `enablejs`」且「仍然沒有任何書籍連結」。這是「這條路通了沒？」最便宜的檢查方式，而且可以避免下一個接手的人從頭再查一次同樣的東西。

## 結論

這次檢查大概花了十五分鐘。

如果略過它、直接去跟 DataDome 硬碰，一個週末的產出會是一個在別人電腦上回 403 的專案，而它證明的能力是「付得起住宅代理」。

十五分鐘的 `curl`，加上一次認真讀完的 robots.txt，重新決定了整個專案的樣子：不同的目標、不同的架構、一套有標準答案可以對照的測試，以及一個別人 clone 下來真的跑得動的 repo。

**先做這個檢查。它是整個專案裡最便宜的一段，也是決定這個專案到底會長成什麼樣的那一段。**
